## 2. 结构性缺口详解

### 2.1 严格预算（高优先级缺口）

**第 9 章要求**：
> 严格预算需要"原子预留、可证明的最大消耗、结算与退款"
> 公式：`可用额度 = 已授权额度 − 已结算消耗 − 在途预留`

**Higress 现状**：
- `ai-token-ratelimit`：请求阶段检查窗口 → 响应后累计 token → **存在并发超额窗口**
- `ai-quota`：请求阶段检查余额 → 响应后扣减 → **同样无法保证并发安全**

**差距本质**：两者都是"先放行后扣减"模式，缺少请求前的**原子预留**机制。在 N 个并发请求同时通过检查但尚未扣减的场景下，实际消耗可能超过预算上限。

**补全路径**：
1. 在请求阶段预留最大可能 token 数（按 `max_tokens` 参数估算）
2. 响应阶段按实际消耗结算，退还预留差额
3. 需要 Redis 事务或 Lua 脚本保证原子性
4. 处理 Redis 故障时的对账恢复

### 2.2 任务归因链路（高优先级缺口）

**第 9 章要求**：
> `task_id → session_id → turn_id → model/tool call → attempt_id`

**Higress 现状**：
- ✅ `session_id`：`ai-statistics` 的 `session_id_header`
- ✅ `model/tool call`：每次调用可记录
- ❌ `task_id`：网关不管理业务任务
- ❌ `turn_id`：网关不区分对话轮次
- ❌ `attempt_id`：无重试尝试标识

**差距本质**：Higress 的统计模型是 **Attempt 级**（每次 model/tool call），不提供 Turn 和 Task 级的聚合。这符合第 9 章的设计原则——网关不承担业务状态的权威所有权——但意味着需要外部系统补全归因链。

**补全路径**：
1. 应用层注入 `task_id` 和 `turn_id` 作为请求头
2. `ai-statistics` 扩展 attributes 配置接收这些头
3. 外部日志/分析系统负责聚合和关联

### 2.3 财务维度隔离（高优先级缺口）

**第 9 章要求**：
> 身份维度和财务维度是正交的，不能混成固定的单一层级

**Higress 现状**：
- 所有治理（限流、配额、统计）围绕 **consumer** 单一维度
- 无组织（Organization）→ 团队（Team）→ 项目（Project）的层级
- consumer 是扁平的身份标识，不支持继承和汇总

**差距本质**：在多租户 SaaS 场景中，需要"团队 A 总配额 100 万 token，其中项目 A1 分配 30 万、项目 A2 分配 20 万"这样的层级配额。Higress 的 consumer 模型无法原生表达这种结构。

**补全路径**：
1. 在 `ai-quota` 上层构建层级配额管理器
2. 或者扩展 consumer 模型支持 group/hierarchy 属性
3. 统计聚合需要支持按层级维度 rollup

## 3. 部分覆盖领域详解

### 3.1 成本感知路由

**现状**：`ai-statistics` 提供 token 用量和模型信息，`model-router` 支持内容路由。但没有内置的"在满足质量要求的前提下选择最低成本模型"的路由器。

**评估**：这更多是应用层或控制面的决策，而非数据面网关的职责。Higress 提供了必要的基础数据（token 统计）和执行能力（路由），但成本决策逻辑需要外部编排。

### 3.2 五种超时

**现状**：
- 连接超时、首字节超时、流式空闲超时：由 Envoy 原生支持
- TTFT：由 `ai-statistics` 统计（观测而非控制）
- 总截止时间：`ai-proxy` 有 `timeout` 字段但当前仅用于获取上下文信息

**差距**：缺少对"总截止时间"的强制执行。在长时间推理任务中，可能需要一个硬性的总时间上限。

### 3.3 审批约束转发

**现状**：
- `ext-auth` 插件支持外部授权服务
- `opa` 插件支持策略引擎
- 但没有内置的"人-in-the-loop"审批工作流

**差距**：第 9 章要求的"待审批不执行 → 批准后重新校验 → 拒绝终止"的完整审批链路需要用户自建审批服务 + `ext-auth` 组合实现。

### 3.4 生成式负载指标

**第 9 章要求补充的指标**：

| 类别 | 要求 | Higress 现状 |
|------|------|-------------|
| 用量与成本 | 输入/输出/缓存 token，价格版本 | ✅ token 统计完整；❌ 无价格版本 |
| 时延 | 建连/首字节/TTFT/空闲/总耗时 | ✅ 大部分可统计 |
| 可靠性 | HTTP 状态/流内错误/取消/重试 | ⚠️ HTTP 状态有；流内错误/取消/重试需扩展 |
| 治理 | 命中策略/拒绝/审批/预算预留 | ⚠️ 限流/拒绝有；审批/预算预留无 |
| 关联 | Task/Session/Turn/Call/Attempt | ⚠️ 仅 Session 和 Call 级 |

**指标基数控制**：第 9 章指出"动态标识更适合日志而非指标标签"。Higress 的 `ai-statistics` 按网关/路由/服务/模型四维度聚合，维度控制合理。但 `task_id` 等高基数标识确实应放在日志中而非指标标签中。

## 4. Higress 的独特优势

虽然存在上述缺口，Higress 在以下方面展现了超越第 9 章基线要求的能力：

### 4.1 66+ LLM 厂商统一代理

`ai-proxy` 覆盖了几乎所有主流 LLM 厂商（国际 + 中国国内），并提供：
- 自动协议检测与转换
- 模型映射与正则匹配
- API Token failover
- 自定义参数覆盖

### 4.2 KV Cache 感知调度

`ai-endpoint-picker` 实现了推理引擎特有的调度优化：
- vLLM KV cache 利用率感知
- 近似前缀缓存匹配（语义 segment LRU）
- LoRA 亲和调度
- Queue depth 感知

这是开源网关中最先进的推理端点调度实现。

### 4.3 语义缓存

`ai-cache` 支持：
- 字符串精确匹配缓存
- 基于向量数据库的语义相似度缓存
- 流式和非流式响应缓存
- 多轮对话缓存键策略

### 4.4 MCP 双轨协议支持

同时支持 MCP 2026-07-28（modern）和历史版本（legacy），包括：
- 协议版本自动协商
- Legacy handshake 兼容
- 完整的 proxy profile 矩阵

### 4.5 Wasm 插件生态

55+ 个 Go Wasm 插件 + 12 个 C++ 插件，覆盖 AI、安全、流量管理、协议转换等全栈场景。热更新、沙箱隔离、多语言支持。

## 5. 建议优先级

| 优先级 | 差距 | 建议 |
|--------|------|------|
| **P0** | 严格预算 | 实现原子预留 + 结算机制，或明确文档标注为"best-effort" |
| **P0** | 任务归因 | 定义标准请求头协议（task_id / turn_id），`ai-statistics` 原生支持 |
| **P1** | 财务维度 | 扩展 consumer 模型支持层级，或提供独立的多租户配额管理器 |
| **P1** | 总截止时间 | `ai-proxy` 的 timeout 应能强制执行总截止时间 |
| **P2** | 审批链路 | 提供审批工作流参考架构（ext-auth + 外部审批服务） |
| **P2** | 流内错误统计 | 扩展 `ai-statistics` 支持 SSE 流内错误和取消的统计 |
| **P2** | 价格版本 | `ai-statistics` 增加 token 单价配置和成本计算 |
| **P3** | 控制面变更链 | 集成 GitOps 工作流实现完整的变更发布链路 |

## 6. 结论

Higress 在 AI 网关的三个治理层面呈现**不均匀但总体领先**的覆盖：

```
LLM Gateway   ████████████████████░░  90%   ← 最完整，仅缺严格预算
MCP Gateway   █████████████████████░  95%   ← 几乎完整覆盖
Agent Gateway ████████░░░░░░░░░░░░░░  40%   ← 基础设施完整，业务语义缺失
统一治理      ██████████████░░░░░░░░  65%   ← 身份映射完整，审批/变更链待补
```

**关键定位**：Higress 正确地把自己定位为**策略执行点**而非**业务状态权威**。第 9 章反复强调"网关不因此获得业务 Task、State、Checkpoint、恢复语义或 Outcome 的权威所有权"——Higress 的设计哲学与此完全一致。差距不在于"Higress 没有做"，而在于"这些职责本就不属于网关"。

**对用户的建议**：
- **个人开发者 / 小团队**：Higress 开箱即用的 LLM 代理 + MCP 托管已足够
- **企业级 AI 平台**：需要在 Higress 之上构建任务归因、层级配额、审批流程等应用层组件
- **成本敏感场景**：关注 `ai-token-ratelimit` 和 `ai-quota` 的并发超额风险，必要时自建严格预算层
